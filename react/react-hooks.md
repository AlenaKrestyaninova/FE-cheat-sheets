# React hooks

## **useState**

``` js
const [value, valueChange] = useState(defaultValue);
```

принимает в качестве параметра начальное значение, то есть на начальном этапе наш value будет иметь значение 1. И возвращает useState массив из двух элементов: первый – состояние, второй – метод, который будет его изменять

- после изменения стейта компонент ререндерится

- асинхронный хук, и он не меняет состояние сразу, он должен ждать повторного рендеринга компонента.

- batching - когда сразу обновляются несколько стейтов, а реакт объединяет их в один ререндер

#### Передать в сеттер значение

``` js
const onClick0 = () => {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
};
```

``` js
// Например count = 0
const onClick0 = () => {
  // count + 1 = 0 + 1;
  setCount(count + 1);
  // Здесь можем ожидать, что count уже 1, но т.к. вызов setState асинхронный
  // состояние еще не изменено, поэтому count по-прежнему 0
  // count + 1 = 0 + 1;
  setCount(count + 1);
  // count + 1 = 0 + 1;
  setCount(count + 1);
}; 
```

#### Передать в сеттер функцию — функциональное обновление состояния

Вместо передачи значения можно передать функцию, которая получает **предыдущее актуальное значение** и возвращает новое

``` js
const onClick1 = () => {
  setCount((v) => v + 1);
  setCount((v) => v + 1);
  setCount((v) => v + 1);
};
```

``` js
// когда новое состояние опирается на предыдущее
const onClick1 = () => {
  setCount(v => v + 1);
// тут состояние уже изменилось
  setCount(v => v + 1);
  setCount(v => v + 1);
};
```

Можно передать функцию в качестве начального значения. Например, когда обрабатываем какие-то данные перед тем, как записать их в качестве начального состояния (не результат вызова функции, а саму функцию, и он сам ее вызовет)

``` js
const prepareData = (data: object): OtherData => {
  console.log('prepareData'); 
  return otherData; // какие-то другие данные (не рабочий код)
}
const [state, setState] = useState(() => prepareData(data))
```

<details open>
<summary>

**Про fiber**

</summary>

- React хранит состояние компонента не в самом компоненте, а в **fiber-узле** (внутренней структуре React), связанной с этим компонентом.
- Каждый вызов `useState` создаёт "ячейку" в связном списке хуков этого fiber-узла. Порядок вызовов хуков должен быть стабильным — отсюда правило "не вызывать хуки условно".
- При вызове `setCount(newValue)` React:
  1.  Помечает компонент как "нуждающийся в обновлении" (schedules an update).

  2.  Запускает **reconciliation** — компонент рендерится повторно с новым значением состояния.

  3.  При повторном рендере `useState(0)` игнорирует начальное значение `0` (оно используется только при первом монтировании) и возвращает актуальное значение из fiber.
- Ленивая инициализация: если начальное значение дорого вычислять, можно передать функцию — `useState(() => expensiveCalc())`, она выполнится только один раз, при монтировании.

</details>
<details open>
<summary>

**Про батчинг**

</summary>

**Батчинг (batching)** — объединение нескольких вызовов `setState` в один ре-рендер, вместо того чтобы рендерить компонент после каждого вызова.

``` js
function handleClick() {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React 18+: будет ОДИН ре-рендер, а не два
}
```

- **До React 18:** батчинг работал только внутри React-обработчиков событий (onClick и т.п.). Внутри промисов, `setTimeout`, нативных event listeners — каждый `setState` вызывал отдельный ре-рендер.
- **React 18+ (automatic batching):** батчинг происходит везде — в промисах, таймерах, нативных обработчиках, — благодаря новому `createRoot` API и внутреннему механизму планирования.

</details>
<details open>
<summary>

**Derived state** — состояние, значение которого можно **вычислить** из других состояний/props, а не хранить отдельно.

</summary>

**Типичные ошибки:**

1.  **Дублирование источника истины.** Хранение вычисляемого значения в отдельном `useState` создаёт риск, что значения "расходятся" (нужно не забыть обновить производное состояние при каждом изменении исходного).

``` js
// ПЛОХО: fullName хранится как отдельный state
const [firstName, setFirstName] = useState('');
const [lastName, setLastName] = useState('');
const [fullName, setFullName] = useState(''); // избыточно!

// ХОРОШО: вычисляем при рендере
const fullName = `${firstName} ${lastName}`;
```

1.  **Синхронизация через useEffect вместо вычисления при рендере:**

``` js
// АНТИПАТТЕРН
useEffect(() => {
  setFullName(`${firstName} ${lastName}`);
}, [firstName, lastName]);
```

Это лишний ре-рендер, задержка на кадр, и лишний источник багов. Правильно — просто вычислить переменную в теле компонента (при необходимости — обернуть в `useMemo`, если вычисление дорогое).

1.  **"Копирование" props в state без причины** (`getDerivedStateFromProps`-антипаттерн):

``` js
// ПЛОХО
function Component({ items }) {
  const [localItems, setLocalItems] = useState(items); // рассинхронизируется при смене props
}
```

Если нужно "сбросить" состояние при смене какого-то ключа — правильнее использовать `key` на компоненте, чтобы React размонтировал/перемонтировал его, а не синхронизировать вручную.

</details>
<details open>
<summary>

**Антипаттерны**

</summary>

1.  **Мутация состояния напрямую:** React сравнивает ссылки (`Object.is`), мутация не создаёт нового объекта → компонент не перерендерится, либо перерендерится с рассинхронизацией.

2.  **Избыточное дробление/дублирование state** (derived state).

3.  **Слишком много состояния в одном родителе** ("state monolith"), из-за чего любое изменение вызывает ре-рендер всего поддерева. Решение — колокация состояния, композиция компонентов, `React.memo`.

4.  **Хранение всего в глобальном сторе "на всякий случай"** — раздувает приложение, усложняет дебаг, provider становится узким местом ре-рендеров.

5.  **Синхронизация состояния через useEffect**, когда можно было просто вычислить значение при рендере (derived state antipattern) или обработать событие в обработчике, а не через эффект.

6.  **Гонки состояний (race conditions) в асинхронных обновлениях**, особенно при незакрытых fetch-запросах при размонтировании компонента (нужна отмена через `AbortController` или флаг `isMounted`/сравнение id запроса).

7.  **Изменение state как побочный эффект рендера** (не в обработчике и не в эффекте) — приводит к бесконечным циклам рендеринга.

8.  **Хранение производных или избыточных вычислений вместо мемоизации** — например, пересортировка массива в state вместо `useMemo`.

</details>

## **useEffect**

-чтобы состояние изменялось не напрямую от действий пользователя, а в следствии внутренней логики программы

- соответствует методам componentDidMount, componentWillUnmount, componentDidUpdate и componentWillUpdate

- асинхронный, будет вызван после рендеринга

Использовать, чтобы

- подписаться на изменение какой-то переменной (стейта или пропса)

- повесить обработчик на события не-реакт элементов (например, mousemove на window)

Про массив зависимостей:

- Нет массива - код запускается каждый раз, когда ваш компонент перерендеривается.

- Пустой массив зависимостей - код запускается только один раз, когда ваш компонент впервые монтируется.

- Непустой массив зависимостей - код запускается каждый раз, когда изменяются какие-либо переменные из массива

``` js
// Монтирование
useEffect(() => {
    // этот код будет выполнен при монтировании компонента (componentDidMount)
}, []);

// Размонтирование
useEffect(() => {
  return () => {
    // этот код будет выполнен при размонтировании компонента (componentWillUnmount)
  }
}, []);

// Монтирование и размонтирование
useEffect(() => {
    // этот код будет выполнен при монтировании компонента (componentDidMount)
  
  return () => {
    // этот код будет выполнен при размонтировании компонента (componentWillUnmount)
  }
}, []);


// Монтирование, размонтирование и обновление
useEffect(() => {
    // этот код будет выполнен при монтировании компонента (componentDidMount)
  // а также после обновления любого элемента из массива зависимостей (componentDidUpdate)
  
  return () => {
    // этот код будет выполнен при размонтировании компонента (componentWillUnmount)
    // а также до обновления любого элемента из массива зависимостей (componentWillUpdate)
  }
}, [dep1, dep2]);
```

##### Сleanup

\- функция хука useEffect, которая позволяет нам останавливать побочные эффекты, которые больше не нужно выполнять, до того, как наш компонент будет размонтирован.  
cleanup - то, что находится в return

``` js
useEffect(() => {
  const fn = () => console.log('handle mousemove');  
  window.addEventListener('mousemove', fn) // обработчик при монтировании компонента; 
  
  return () => { // это cleanup - удалим обработчик при размонтировании компонента
    window.removeEventListener('mousemove', fn);
  };
}, []); // массив зависимостей пустой - эффект сработает строго при монтировании/размонтировании
```

## **useLayoutEffect**

\- синхронный и будет вызван **до** того, как браузер сможет отрисовать компоненты. Срабатывает когда компоненты уже находятся на virtual dom (в памяти и можно прочитать/установить различные свойств), но еще не были отрисованы браузером. Предотвращает лишнее обновление компонента

**useEffect** (изменение произойдёт после рендера):

``` js
const [value, setValue] = useState(0);

useEffect(() => {
  // Изменение состояния будет происходить после выполнения всего кода
  // компонента, в том числе рендеринга dom элементов
  // изменение состояния запустит повторное выполнение кода компонента
  // в том числе и рендеринг
  setValue(level + Math.random() * 200);
}, [level]);
```

**useLayoutEffect** (изменение произойдёт до отрисовки):

``` js
const [value, setValue] = useState(0);

useLayotEffect(() => {
  // Изменение состояние будет происходить до фазы рендеринга
  // что сделает код более производительным
  setValue(level + Math.random() * 200);
}, [level]);
```

## **useContext**

React Context API - это интерфейс, который позволяет сохранять некоторую величину (переменную или объект), и использовать ее между несколькими компонентами. Контекст - сохраненная величина.

Интерфейс react-контекста состоит из метода createContext, компонента Context.Provider и хука useContext.

1.  Инициализировать контекст в том же месте, где инициализируется приложение

    ``` js
    // Параметром передается значение по умолчанию
    // Имя контекста выбирается произвольно
    const UserContext = React.createContext({})
    ```

2.  Подключить провайдер и передать данные в контекст через пропс value.

``` js
<UserContext.Provider value={user}> // user — данные которые лежат внутри контекста
  <MyComponent />
</UserContext.Provider>
```

1.  Получить данные контекста

``` js
import React, { useContext } from 'react'
const MyComponent = () => {
  const user = useContext(UserContext) // Возвращает контекст целиком
  return <h1>{user.name}</h1>
}
```

## **useRef**

когда необходимо обратиться к какому-то DOM-объекту напрямую

``` js
const App = () => {
  const ref = useRef();
 
  useEffect(() => {
    console.log(ref.current);
  }, []);
 
  return <div ref={ref} />;
};
```

- можно **сохранять информацию** между повторными рендерами (в отличие от обычных переменных, которые сбрасываются при каждом рендере).

- изменение **не вызывает повторного рендеринга** (в отличие от переменных состояния, которые вызывают повторный рендеринг).

- Информация **является локальной** для каждой копии вашего компонента (в отличие от внешних переменных, которые являются общими).

``` js
import { useRef } from 'react';
// Счетчик кликов
export default function Counter() {
    let ref = useRef(0);

    function handleClick() {
        ref.current = ref.current + 1;
        alert('You clicked ' + ref.current + ' times!');
    }
// ref.current в разметке обновляться не будет
    return <button onClick={handleClick}>Click me!</button>;
```

Можно манипулировать DOM-элементами

``` js
export default function Form() {
    const inputRef = useRef(null); // начальное значение null
    function handleClick() {
        inputRef.current.focus();
    }
    return (
        <>
            <input ref={inputRef} /> // передать объект ref в качестве атрибута ref в JSX узла DOM
            <button onClick={handleClick}>
                Focus the input
            </button>
        </>
    );
// после рендера React установит свойство current объекта ref на этот DOM-узел
}
```

## **useReducer**

позволяет вынести данные из компонентов. - можно отобразить данные в любом компоненте *(одно состояние, сложные переходы)*

``` js
const initialState = {count: 0};
 
function reducer(state, action) {
  switch (action.type) {
    case "increment":
      return { ...state, count: state.count + 1 };
    case "decrement":
      return { ...state, count: state.count - 1 };
    default:
      throw new Error();
  }
}
 
const App = () => {
  const [state, dispatch] = useReducer(reducer, initialState);
 
  return (
    <>
      {state.count}
      <button onClick={() => dispatch({type: "decrement"})}>-</button>
      <button onClick={() => dispatch({type: "increment"})}>+</button>
    </>
  );
};
```

<details open>
<summary>

**Когда useReducer предпочтительнее useState**

</summary>

- **Сложная логика обновления**, когда несколько связанных значений state обновляются вместе, и легко забыть обновить одно из них при использовании нескольких `useState`.
- **Следующее состояние зависит от предыдущего сложным образом**, а не просто "прибавить 1".
- **Много разных типов обновлений (actions)** одного и того же состояния — читаемость через `switch` в редьюсере выше, чем через набор inline-обработчиков.
- **Тестируемость**: редьюсер — чистая функция, её легко тестировать отдельно от компонента, без рендеринга.
- **Передача только `dispatch` вглубь дерева** через контекст, вместо множества функций-сеттеров — `dispatch` стабилен между рендерами (не нужен в зависимостях `useEffect`/`useCallback`), в отличие от инлайновых обработчиков.
- Полезен как более простая альтернатива Redux, когда нужна структурированность, но глобальный стейт-менеджер избыточен.

</details>

## **useMemo**

для оптимизации вычислений

``` js
const MyComponent = ({a, b}) => {
  const sqrt = useMemo(() => a * a, [a]); // функция обернута в хук, передали коллбек и массив зависимостей. Когда меняется а - вычисляется заново 
 
  return (
    <div>
      <div>А в квадрате: {sqrt}</div>
      <div>B: {b}</div>
    </div>
  );
};
```

## **useCallback**

-для мемоизации функций - возвращает одну и туже ссылку на функцию, до тех пор, пока не изменится одна из зависимостей.

- при первом рендере - вернет функцию (не вызовет)

- при следующих рендерах - тоже вернет функцию, но не вызовет

- при изменении зависимостей создается новый экземпляр функции

**Когда использовать?**

- Если функция передаётся в дочерний компонент, который использует React.memo (чтобы не рендерить зря).

- Если функция является зависимостью в useEffect, чтобы эффект не срабатывал без необходимости.

``` js
function MyComponent() {
  const [count, setCount] = React.useState(0);

  // Мемоизация функции
  const handleClick = useCallback(() => {
    console.log(count);
  }, [count]); // Зависимости: функция обновится, только если изменится count

  return <ChildComponent onClick={handleClick} />;
}

// Дочерний компонент с React.memo
const ChildComponent = React.memo(({ onClick }) => {
  return <button onClick={onClick}>Click me</button>;
});
```

## React.memo

позволяет пропустить повторное отображение компонента, если его пропсы неизменны. Компонент не перерендерится, если обновился родитель

``` js
const Greeting = memo(function Greeting({ name }) {
    return <h1>Hello, {name}!</h1>;
});

export default Greeting;
```

**Не использовать, когда**:

1.  Когда компонент обертывает другие компоненты, позвольте ему [принимать JSX в качестве дочерних компонентов](https://reactdev.ru/learn/passing-props-to-a-component/) Таким образом, когда компонент-обертка обновляет свое собственное состояние, React знает, что его дочерние компоненты не нужно перерисовывать.

2.  Предпочитайте локальное состояние и не [поднимайте состояние вверх](https://reactdev.ru/learn/sharing-state-between-components/) дальше, чем это необходимо. Например, не храните переходные состояния, такие как формы и то, наведен ли элемент на вершину вашего дерева, в глобальной библиотеке состояний.

3.  Сохраняйте чистоту [логики рендеринга](https://reactdev.ru/learn/keeping-components-pure/) Если повторный рендеринг компонента вызывает проблему или приводит к заметным визуальным артефактам, это ошибка в вашем компоненте! Исправьте ошибку вместо того, чтобы добавлять мемоизацию.

4.  Избегайте [ненужных Эффектов, обновляющих состояние](https://reactdev.ru/learn/you-might-not-need-an-effect/) Большинство проблем с производительностью в приложениях React вызваны цепочками обновлений, исходящих от Эффектов, которые заставляют ваши компоненты рендериться снова и снова.

5.  Попробуйте [удалить ненужные зависимости из ваших Эффектов](https://reactdev.ru/learn/removing-effect-dependencies/). Например, вместо мемоизации часто проще переместить какой-то объект или функцию внутрь Эффекта или за пределы компонента.

Как заигнорить один из пропсов

``` js
const UserCard = ((name, age, pet) => {

})

const areEqual = (prevProps, nextProps) => {return prevProps.name === nextProps.name;}; // если функ возвращает true, пропсы будут равны, компонент не будет перерендериваться

const areEqualPets = (prevProps, nextProps) => {return prevProps.pet === nextProps.pet;};

export default React.memo(UserCard, areEqual, areEqualPets);
```
