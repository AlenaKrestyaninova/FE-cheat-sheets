# SSR и серверный рендеринг

### 1. Что такое SSR и зачем он нужен

**SSR (Server-Side Rendering)** — это подход, при котором HTML страницы генерируется на сервере (на основе компонентов React/Vue/др.) и отправляется браузеру уже готовым, а не собирается с нуля в браузере из JS-бандла.

Зачем:

-   **Быстрый первый рендер (FCP/LCP)** — пользователь видит контент до того, как загрузился и выполнился весь JS.

-   **SEO** — поисковые роботы получают готовый HTML с контентом, а не пустой `<div id="root">`.

-   **Работа на слабых устройствах/медленном интернете** — не нужно ждать загрузки и выполнения тяжёлого JS-бандла, чтобы увидеть контент.

-   **Соцсети и превью** (Open Graph, Twitter Cards) — боты соцсетей часто не выполняют JS.

Противопоставляется **CSR (Client-Side Rendering)**, где сервер отдаёт почти пустой HTML, а весь UI собирается в браузере после загрузки JS.

---

### 2. Гидратация и дегидратация

**Гидратация (hydration)** — процесс "оживления" статического HTML, полученного от сервера: React проходит по уже существующему DOM-дереву, сопоставляет его со своим виртуальным деревом компонентов и "навешивает" event-хендлеры, стейт, эффекты — превращая статичную разметку в полноценное интерактивное приложение. Ключевая идея: **DOM не создаётся заново**, React переиспользует существующие узлы.

**Дегидратация** — обратный процесс, часто используется в контексте передачи данных: сервер "дегидрирует" (сериализует) состояние приложения (например, результат запросов данных) в JSON, встраивает его в HTML (`<script>window.__DATA__=...</script>`), а на клиенте это состояние "гидрируется" обратно в объекты JS, чтобы не делать повторные запросы при старте клиента.

Также термин используется в React Query/SWR — "dehydrate/hydrate" стейт кэша между сервером и клиентом.

---

### 3. Почему возникает hydration mismatch

Ошибка происходит, когда **HTML, сгенерированный на сервере, не совпадает с тем, что React ожидает получить при первом клиентском рендере**. React в этом случае либо предупреждает в консоли, либо перестраивает DOM (что убивает выгоду SSR и может вызвать "мигание" контента).

Типичные причины:

-   **Использование данных, доступных только в браузере**: `window`, `localStorage`, `navigator`, размеры экрана — на сервере их нет, значения отличаются.

-   **Дата/время**: `new Date()` или `Math.random()` дают разные значения на сервере и клиенте.

-   **Условный рендеринг по окружению**: `typeof window !== 'undefined' ? A : B` — на сервере рендерится B, на клиенте A.

-   **Расширения браузера**, модифицирующие DOM до гидратации (классическая причина шумных warning'ов, но не связанная с кодом).

-   **Локаль/таймзона** — сервер и клиент рендерят даты по-разному.

-   **Невалидный HTML** — например, `<div>` внутри `<p>`, из-за чего браузер сам перестраивает DOM ещё до того, как React его увидит.

Решение: гарантировать детерминированность рендера (одинаковый результат на сервере и клиенте при первом проходе), а данные, зависящие от браузера, применять только после монтирования (`useEffect`), либо явно помечать компонент как client-only с "заглушкой" на этапе SSR.

### 4. SSG и его отличие от SSR

**SSG (Static Site Generation)** — HTML генерируется **один раз на этапе сборки** (build time), а не на каждый запрос. Готовые HTML-файлы затем раздаются как статика (можно кешировать на CDN).

Отличия от SSR:

|  | SSR | SSG |
| --- | --- | --- |
| Когда рендерится | На каждый запрос (runtime) | Один раз при сборке (build time) |
| Актуальность данных | Всегда свежие | "Замороженные" на момент сборки |
| Нагрузка на сервер | Есть (рендер на каждый запрос) | Минимальная (просто раздача файлов) |
| Скорость ответа | Зависит от сервера/данных | Максимальная (статика + CDN) |
| Подходит для | Часто меняющийся контент, персонализация (дашборды, личный кабинет) | Блоги, документация, маркетинговые страницы, каталоги без частых изменений |

---

### 5. Что такое ISR

**ISR (Incremental Static Regeneration)** — гибрид SSG и SSR (концепция из Next.js). Страница генерируется статически (как в SSG), но может **перегенерироваться в фоне** через заданный интервал времени (`revalidate`) или по требованию (on-demand revalidation), без полной пересборки всего сайта.

Как работает:

1.  Первый запрос отдаёт закешированную (старую) статическую версию.

2.  Если прошло больше времени, чем `revalidate`, сервер в фоне генерирует новую версию страницы.

3.  Следующие запросы получают уже обновлённую версию (стратегия stale-while-revalidate).

Плюс: сочетает скорость статики с относительной свежестью данных, без необходимости пересобирать весь проект при каждом изменении контента.

---

### 6. Как определяется граница между клиентской и серверной логикой

Это зависит от фреймворка, но общие принципы:

-   **По умолчанию SSR** — то, что не требует интерактивности (браузерных API, event-хендлеров, состояния), рендерится на сервере.

-   **Явные маркеры**: в Next.js App Router, например, директива `"use client"` в начале файла помечает компонент и его поддерево как клиентские; всё остальное по умолчанию — Server Components.

-   **Критерии, что должно быть клиентским**:

    -   Использование `useState`, `useEffect`, `useReducer` и других хуков с состоянием/эффектами.

    -   Обработчики событий (`onClick`, `onChange` и т.п.).

    -   Доступ к браузерным API (`window`, `document`, `localStorage`).

    -   Библиотеки, завязанные на DOM (некоторые графики, drag-n-drop).

-   **Критерии, что можно/нужно оставить на сервере**:

    -   Получение данных (fetch к БД, API) — ближе к источнику данных, без лишнего JS на клиенте.

    -   Статичная разметка, не требующая интерактивности.

    -   Тяжёлые зависимости, которые не нужно тащить в клиентский бандл (парсинг markdown, работа с секретами/API-ключами).

Практическое правило: **серверные компоненты — по умолчанию, клиентские — точечно**, там, где действительно нужна интерактивность. Это уменьшает размер JS-бандла, отправляемого клиенту.
