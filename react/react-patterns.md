# React patterns - шаблоны проектирования

## **Container + Presentational Components**

Разделение компонентов на умные и тупые

- контейнерные компоненты - умные
- презентационные - тупые, визуальные

Presentational Components
- отвечают только за то, как что-то выглядит.
- получают данные через props и отображают их.
- чистые функциональные компоненты, часто без собственного состояния

Container Components,
- знают, что показать и откуда это взять,
- не занимаются отображением.
- содержат в себе всю логику

Плюсы и минусы:
+ чёткое разделение обязанностей,
+ возможность переиспользовать и заменять части независимо
+ облегчение тестирования.
- появляется больше файлов/компонентов,
- усложняет структуру

## **Higher-Order Component (HOC)**

это функция, которая принимает React-компонент и возвращает новый компонент

это «обёртка». Мы помещаем один компонент внутрь другого, чтобы на выходе получить расширенную версию переданного в HOC компонента.

Например: у нас есть несколько разных компонентов, и всем им нужно что-то общее: например, обработка ошибок или подписка на внешние данные. Можно было бы скопировать этот код в каждый из компонентов, но куда элегантнее написать HOC один раз и применить ко всем.

```
function withCounter(WrappedComponent) {
  // Возвращаем новый компонент-обёртку
  return function WithCounter(props) {
    const [count, setCount] = useState(0);
    // Передаем внутрь исходного компонента счётчик и функцию для увеличения
    return <WrappedComponent count={count} increment={() => setCount(c => c + 1)} {...props} />;
  };
}
// Использование HOC:
function ClickButton({ count, increment, label }) {
  return <button onClick={increment}>{label}: {count}</button>;
}
const EnhancedButton = withCounter(ClickButton);
```

Плюсы и минусы
+ один HOC может добавить функциональность множеству компонентов сразу — не надо копировать код везде.
+ HOC можно комбинировать: например, обернуть компонент сначала в HOC, добавляющий тему оформления, потом в HOC, добавляющий логирование, и т.д. В итоге получим компонент, обладающий сразу несколькими дополнительными возможностями.
- усложнение структуры.
- сложно дебажить
- конфликты имён (нужно следить, чтобы, например, `prop.title` от HOC не перезаписал пропс title, который вы передали самому компоненту).
- усложняют типизацию в TypeScript (надо правильно описывать generic для пропсов)

## **Render Props**

— это подход, когда компонент сам не рендерит что-то внутри себя, а принимает функцию (часто через проп render или просто используя детей как функцию) и вызывает её, чтобы получить содержимое. То есть мы передаём компоненту инструкцию, что именно отрендерить, а он сам обеспечивает, когда и с какими данными вызвать эту инструкцию.

```
function FilteredList({ items, filter, children }) {
  const filtered = items.filter(filter);
  // Вызываем функцию-ребёнка для каждого элемента, оборачивая в <ul>
  return <ul>{filtered.map(item => children(item))}</ul>;
}

// Использование:
<FilteredList items={[1,2,3,4,5]} filter={n => n % 2 === 0}>
  {item => <li key={item}>{item}</li>}
</FilteredList>
```

`<FilteredList>` знает, как отфильтровать массив `(items.filter(filter))`, но не знает, как отрисовать каждый элемент. Вместо этого он вызывает функцию, которую мы передали в качестве дочернего элемента (children), для каждого элемента списка. Эта функция возвращает `<li>` для каждого item. В результате логика фильтрации инкапсулируется внутри `FilteredList`, а конкретное отображение списка задаётся извне.

Плюсы и минусы:
+ компонент-провайдер максимально универсальный, а конкретную разметку делегировать наружу.
- излишний шум в JSX.
- каждый раз при рендере создаётся новая функция - плохая производительность.
- грустно типизировать

## **Хуки и кастомные хуки**

- для повторного использования логики

```
function useCounter(initialValue = 0) {
  const [count, setCount] = useState(initialValue);
  const increment = () => setCount(c => c + 1);
  return { count, increment };
}
// Использование хука в компоненте:
function ClickButton({ label }) {
  const { count, increment } = useCounter();
  return <button onClick={increment}>{label}: {count}</button>;
}
```

Плюсы и минусы:
+ ясность и лаконичность.
+ легко тестировать (это по сути просто функции).
+ позволяют разделять логику внутри одного компонента на независимые части
- вызывать только в компонентах либо других хуках, не внутри условий.
- повторное использование хука означает, что каждый компонент получает свою копию состояния.

## **Compound Components (Составные компоненты)**

— это паттерн, при котором несколько компонентов работают вместе как единое целое, обмениваясь общим состоянием (обычно через контекст)

1.  родитель (компонент-контейнер) содержит всё состояние (например, какой пункт раскрыт) и методы управления (функция `toggle(index)`)- это контекст.

2.  родитель children своим контекст провайдером и передаёт туда эти данные и функции.

3.  Дочерние компоненты (которые рендерятся где-то внутри `children`) просто берут нужное из контекста и получают доступ к состоянию родителя. Они знают, к какому именно контейнеру принадлежат, благодаря тому, что рендерятся внутри него и получают его контекст.

```
const ToggleContext = createContext();
function Toggle({ children }) { // <Toggle> управляет состоянием on (показано/скрыто) и предоставляет через контекст значение { on, toggle } всем потомкам
  const [on, setOn] = useState(false);
  const toggle = () => setOn(prev => !prev);
  return (
    <ToggleContext.Provider value={{ on, toggle }}>
      {children}
    </ToggleContext.Provider>
  );
}
function ToggleOn({ children }) { //  <ToggleButton> получает из контекста функцию toggle и вызывает её при клике.
  const { on } = useContext(ToggleContext);
  return on ? <>{children}</> : null;
}
function ToggleOff({ children }) {
  const { on } = useContext(ToggleContext);
  return on ? null : <>{children}</>;
}
function ToggleButton({ children }) {
  const { toggle } = useContext(ToggleContext);
  return <button onClick={toggle}>{children}</button>;
}
// Использование:
<Toggle>
  <ToggleOn>Теперь мы видим скрытый текст</ToggleOn>
  <ToggleOff>Текст скрыт</ToggleOff>
  <ToggleButton>Переключить</ToggleButton>
</Toggle>
```

Плюсы и минусы:
+ огромная гибкость и выразительность.
+ возможность тонко настроить итоговую разметку, вставить дополнительные элементы если надо, ведь внутри children мы не ограничены,
+ Проще поддерживать визуальное единообразие: все части контролируются одним контекстом, не размазывая логику по нескольким несвязанным компонентам.
- сложнее реализовать. -если `<ToggleButton>` случайно использовать вне `<Toggle>` (то есть вне своего провайдера), useContext вернёт undefined и будет ошибка — надо либо избегать такого, либо делать проверки и бросать понятное сообщение об ошибке .
- когда контекстное значение меняется, все потребители контекста перерендерятся. - плохая производительность

## Suspense

- позволяет "приостанавливать" рендеринг компонента до завершения асинхронной операции, показывая fallback UI.
Компонент "бросает" промис вместо JSX. Suspense ловит этот промис, показывает fallback, и перерендеривает компонент когда промис резолвится.

**1\. Lazy loading компонентов:**

```
const LazyComponent = lazy(() => import('./MyComponent'));

<Suspense fallback={<div>Загрузка...</div>}>
  <LazyComponent />
</Suspense>
```

**2\. Data fetching (с библиотеками типа SWR, React Query):**

```
<Suspense fallback={<Spinner />}>
  <UserProfile userId={123} />
</Suspense>
```

Плюсы:
+ Убирает императивные loading состояния
+ Лучший UX через композицию границ загрузки
+ Работает с React 18 concurrent features
+ превращает асинхронные операции из императивного кода в декларативную разметку.

## React Server Components - серверные компоненты

Компонент выполняется на сервере, имеет доступ к базе данных/файлам, и клиент получает готовую разметку без JavaScript-кода компонента.

Типы компонентов

```
// UserProfile.server.js
async function UserProfile({ userId }) {
  const user = await db.users.find(userId); // Прямой доступ к БД!
  return <div>{user.name}</div>;
}
```

- Читать файлы, обращаться к БД
- Использовать серверные библиотеки
- НЕ отправляются в бандл

```
'use client'; // директива

function Counter() {
  const [count, setCount] = useState(0); // Интерактивность
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

- Использовать хуки (useState, useEffect)
- Обрабатывать события
- Работать с браузерными API

Плюсы и минусы
+ Меньший размер бандла
+ Быстрый доступ к данным на сервере
+ Автоматическое кеширование
+ SEO-friendly
- Нет состояния и эффектов
- Нет браузерных API
- Нельзя передавать функции как пропы
